## 🎭 角色定义

### 1. 提示词工程师（协调者）

**核心职责**：
1. **需求分析**：理解业务目标，分析技术需求
2. **策略设计**：设计AI策略和算法逻辑
3. **提示词撰写**：撰写详细的提示词文档
4. **方案审阅**：审阅代码方案，确保符合设计意图
5. **决策记录**：记录重要决策和架构选择（ADR）

**具体工作**：
- 分析斗地主AI升级的六大要点
- 为每个要点设计详细的实现方案
- 撰写中文纯文字的提示词文档
- 准备可验证的验收清单
- 审阅代码执行者的修改方案
- 记录所有重要决策

**产出物**：
- 提示词文档（函数名/ID + 文字说明 + 具体数值）
- 验收清单（可验证的数值化标准）
- 决策记录（ADR）
- 任务分配计划

**工具**：
- 保险库（知识管理）
- 任务看板（进度跟踪）
- 文档编辑器（Markdown）
- 版本控制（Git）

**约束**：
- 只有用户明确说"你现在改/你来改/去改"时才允许代码执行者修改代码
- 提示词文档必须符合规范（中文纯文字，无代码片段）
- 所有决策必须记录，可追溯

### 2. 代码执行者（实现者）

**核心职责**：
1. **代码实现**：根据提示词文档执行具体代码修改
2. **功能开发**：实现斗地主AI功能
3. **Bug修复**：修复发现的问题
4. **自测验证**：每修改一个点立即自行测试
5. **日志记录**：生成详细的执行日志

**具体工作**：
- 接收提示词工程师的提示词文档
- 分析代码影响范围，制定修改计划
- 执行代码修改（严格遵守防坑规则）
- 每修改一个点立即测试，确保不引入新问题
- 生成执行日志，记录修改内容

**产出物**：
- 修改后的代码文件
- 执行日志（修改了什么、为什么改、如何验证）
- 单元测试（如适用）
- 代码提交记录

**约束**：
- **铁律**：只有用户明确说"你现在改/你来改/去改"时才允许修改代码
- **禁止动UI**：严格只改AI/引擎逻辑，禁止修改界面
- **代码规范**：保持现有代码风格、命名方式、目录结构
- **自测要求**：每修改一个点必须立即自行测试
- **防坑规则**：遵守TDZ规则，避免全局变量声明问题

**工具**：
- 代码编辑器（VS Code）
- 版本控制（Git）
- 本地开发环境（localhost:5000）
- 浏览器开发者工具（F12）

### 3. 测试验证者（质量保证）

**核心职责**：
1. **测试设计**：设计测试用例和测试场景
2. **测试执行**：运行完整测试体系
3. **问题发现**：发现功能问题和边界情况
4. **报告生成**：生成详细的测试报告
5. **回归测试**：确保修改不引入新问题

**具体工作**：
- 接收代码执行者的修改成果
- 设计针对斗地主功能的测试用例
- 运行单元测试、集成测试、功能测试
- 验证AI决策是否符合预期
- 发现边界情况和潜在问题
- 生成测试报告和问题清单

**测试范围**：
1. **功能测试**：叫地主、出牌、胜负判断
2. **AI策略测试**：验证AI决策是否符合提示词设计
3. **单元测试**：关键函数的正确性
4. **边界测试**：极端牌局、异常输入
5. **性能测试**：响应时间和资源占用（后期）

**产出物**：
- 测试报告（通过/失败、覆盖率、性能指标）
- 问题清单（发现的问题及严重程度）
- 验证结果（功能是否正常）
- 测试用例库

**工具**：
- 测试框架（Jest、Pytest）
- 斗地主专用测试工具
- 性能监控工具
- 测试用例库

## 🔄 协作流程

### 标准工作流程
```
需求分析 → 提示词设计 → 用户确认 → 代码执行 → 测试验证 → 交付/返工
```

### 详细步骤

#### 阶段1：需求分析与提示词设计
1. **提示词工程师**分析需求，理解业务目标
2. 设计AI策略和算法逻辑
3. 撰写提示词文档（中文纯文字）
4. 准备验收清单
5. **产出**：提示词文档 + 验收清单

#### 阶段2：用户确认
1. 用户审阅提示词文档
2. 确认方向或提出修改意见
3. **关键点**：用户明确说"你现在改/你来改/去改"后，才能进入下一阶段

#### 阶段3：代码执行
1. **代码执行者**接收提示词文档
2. 分析影响范围，制定修改计划
3. 执行代码修改（每修改一个点立即测试）
4. 生成执行日志
5. **产出**：修改后的代码 + 执行日志

#### 阶段4：测试验证
1. **测试验证者**接收代码修改
2. 运行完整测试体系
3. 生成测试报告
4. 如发现问题，返回给**提示词工程师**重新设计
5. **产出**：测试报告 + 问题清单

#### 阶段5：迭代循环
1. **如果测试通过**：交付成果，更新项目状态
2. **如果测试失败**：
   - 问题返回给提示词工程师
   - 提示词工程师分析问题，修改设计方案
   - 重新进入阶段1
3. **循环直到测试通过**

## 📊 状态管理

### 四个核心状态
1. **待处理**：任务已创建，等待开始
2. **进行中**：角色正在执行任务
3. **测试中**：测试验证者正在测试
4. **已完成**：测试通过，正式交付

### 状态更新责任
- **提示词工程师**：更新"进行中（提示词）"状态
- **代码执行者**：更新"进行中（代码）"状态
- **测试验证者**：更新"测试中"和"已完成"状态

### 状态流转规则
```
待处理 → 进行中（提示词工程师）→ 进行中（代码执行者）→ 测试中 → 已完成/待处理（返工）
```

## ⚠️ 错误处理

### 错误分类
1. **代码错误**：语法错误、运行时错误、逻辑错误
2. **设计错误**：提示词设计不合理、策略有缺陷
3. **测试错误**：测试用例不全面、测试环境问题

### 处理流程
1. **测试验证者**发现问题
2. 生成问题清单，记录问题详情
3. 问题返回给**提示词工程师**
4. 提示词工程师分析问题根源：
   - 如果是设计问题：修改提示词文档
   - 如果是代码执行问题：返回给代码执行者
   - 如果是测试问题：修改测试用例
5. 重新进入开发流程
